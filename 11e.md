### Question 2: Let’s assume your app needs a database. How could you do that?
Since GitHub Pages only hosts static web files (HTML, CSS, and client-side JavaScript), you cannot host a traditional server-side database directly inside the repository. To solve this, you could:
* **Option 1 (Serverless / Backend-as-a-Service):** Use a cloud-based database service like **Firebase**, **Supabase**, or **MongoDB Atlas** that offers a direct JavaScript API. This allows the frontend hosted on GitHub Pages to read and write data securely via API calls.
* **Option 2 (Separate Backend):** Keep the frontend on GitHub Pages and connect it to an external backend API (hosted on platforms like Render, Heroku, or AWS), which in turn communicates with a standard relational database (like PostgreSQL or MySQL).

### Question 3: Change the GitHub Pages deployment so that a new version is published only when a new tag is pushed. Is this possible? If so, explain how you implemented it.
**Yes, this is completely possible.** However, it cannot be done using the default "Deploy from a branch" setting in GitHub Pages. Instead, you have to switch the deployment source to **GitHub Actions** and use a custom workflow.

**Implementation Steps:**
1. In the repository settings under **Pages**, change the deployment source from *Deploy from a branch* to **GitHub Actions**.
2. Create a custom workflow file in your repository at `.github/workflows/deploy.yml`.
3. Configure the `on:` trigger in the configuration file to strictly target tags instead of branch commits. The workflow trigger configuration looks like this:

```yaml
on:
  push:
    tags:
      - 'v*' # This ensures the deployment pipeline only runs when a tag starting with 'v' is pushed
```
By setting this up, regular code commits to the `main` branch will be ignored by the deployment pipeline, and a new website version will only be published when a release tag is pushed.
